Cotizar una automatización incluyendo pruebas, consumo y soporte

Define cuándo funciona una automatización, qué ocurre cuando falla y cuánto trabajo queda después de ponerla en marcha.

Cotiza un recorrido concreto, no «automatizar el negocio»

Empieza por identificar entrada, transformación, salida y responsable. Un flujo que recibe solicitudes, propone una categoría y espera aprobación tiene requisitos distintos de otro que ejecuta acciones sin supervisión. La presencia de una herramienta de IA tampoco elimina el trabajo de integración, pruebas y seguimiento.

Usaremos un caso hipotético: un formulario envía solicitudes a una hoja, un modelo sugiere una categoría y una persona confirma el resultado antes de crear una tarea. Se conecta un formulario, una hoja y un tablero existentes. Las pruebas usan datos sintéticos. No se promete una precisión universal ni se incluyen decisiones automáticas sobre pagos.

Presupuesto que incluye probar las excepciones

ActividadHoras hipotéticas
Diagnóstico y definición del flujo6
Integración y configuración9
Pruebas y corrección de fallos7
Documentación operativa3
Entrega y formación3
Total28

A una tarifa interna elegida de 30 unidades por hora, el trabajo suma 28 × 30 = 840. Se autoriza además un límite hipotético de 60 para consumo durante pruebas: el máximo previsto es 900 antes de impuestos aplicables. Ese límite no es una tarifa del proveedor. Registra el consumo real y acuerda cómo se tratará la parte no utilizada.

Convierte «funciona» en criterios observables

Prepara una tabla de casos: solicitud válida, campo obligatorio vacío, entrada duplicada, categoría ambigua, servicio externo no disponible y aprobación rechazada. Para cada caso escribe resultado esperado, resultado observado y evidencia. Un caso normal que termina correctamente no demuestra que el sistema pueda recuperarse de un fallo.

Define cómo se reconoce una solicitud ya procesada para evitar tareas duplicadas. Comprueba qué sucede si una respuesta externa llega tarde y el envío se repite. Las solicitudes ambiguas deben quedar pendientes de revisión según el alcance de este ejemplo. Acordar un conjunto de pruebas permite aceptar la entrega; no convierte esa muestra en una garantía para todos los datos futuros.

Separa consumo, soporte y nuevas funciones

El consumo posterior depende del volumen, los servicios usados y sus condiciones vigentes. Estima un escenario con datos del cliente y comprueba las tarifas publicadas por cada proveedor, indicando cuándo se consultaron. Evita llamar «ilimitado» a un flujo sujeto a cuotas, límites o costos por solicitud.

Un soporte mensual hipotético de cuatro horas a 30 costaría 120, aparte del consumo externo. Define si cubre revisar alertas, corregir incidencias del alcance original y responder consultas; indica el horario y el plazo de respuesta acordados. Distingue la corrección de un defecto de entrega de un servicio continuo, según las condiciones del contrato.

Deja un procedimiento para detener y recuperar

La documentación debe explicar cómo pausar el flujo, localizar solicitudes pendientes y reanudarlas sin duplicación. Incluye quién conserva las cuentas, cómo se conceden y retiran accesos, y dónde se registran errores sin exponer información innecesaria. Entrega credenciales mediante el canal seguro acordado, nunca dentro de un manual compartido.

Si el cliente pide conectar un segundo formulario con campos distintos, realiza una evaluación. Supongamos tres horas de mapeo y tres de pruebas: 6 × 30 = 180 de trabajo adicional. Confirma también si cambia el consumo o la documentación y aprueba la ampliación antes de activarla.

  • ¿Quién revisará las solicitudes que el sistema no puede resolver?
  • ¿Qué volumen y datos deben admitirse?
  • ¿Qué prueba permite aceptar cada integración?
  • ¿Quién recibe alertas cuando una dependencia falla?

Calcula tus horas con la calculadora freelance y separa implementación, consumo y soporte en el generador de presupuestos.
